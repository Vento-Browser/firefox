# Фингерпринтинг в Vento — исследование (этап 1)

Asana: https://app.asana.com/1/1216608809930980/project/1216609614088977/task/1203867458889959

## 0. Постановка задачи и ключевое отличие от Firefox RFP

Задача Vento: сделать так, чтобы **два разных человека на двух разных
компьютерах**, у которых в Vento-панели заданы одни и те же параметры
фингерпринт-профиля, для любого сайта выглядели как **один и тот же компьютер**
— на 100%, детерминированно и настраиваемо.

Это НЕ то же самое, что делает штатный Firefox. У Firefox два режима, и оба нам
не подходят «как есть»:

| Режим Firefox | Что делает | Годится ли для Vento |
|---|---|---|
| **RFP** (`privacy.resistFingerprinting`) | Приводит значения к **общей универсальной болванке** (generic profile): фикс. UA, экран, часовой пояс UTC, набор шрифтов и т.д. Цель — «раствориться в толпе RFP-пользователей». | **Частично.** Многие поля уже прибиты к константам — это ровно то, что нужно. Но болванка НЕ настраиваемая, и часть значений **рандомизируется** (canvas/webgl-шум) — это противоположность нашей цели. |
| **FPP** (`privacy.fingerprintingProtection`) | Точечная защита + **рандомизация** canvas/WebGL по **случайному ключу сессии**. Цель — чтобы каждый выглядел **по-разному** (в т.ч. один и тот же юзер по-разному в разных сессиях/доменах). | **Нет.** Прямо противоречит задаче: нам нужна детерминированная идентичность, а не случайность. |

Вывод: инфраструктура Firefox RFP/FPP — отличная **точка входа и каркас**
(перечень поверхностей, механизм таргетов, точки перехвата уже есть), но
логику надо развернуть из «универсально/случайно» в **«детерминированно из
общего seed-профиля»**.

### Ключевая техническая находка

Рандомизация canvas в Firefox завязана на **случайный UUID сессии**:
`nsRFPService::GetBrowsingSessionKey()` делает
`mBrowsingSessionKeys.InsertOrUpdate(oaSuffix, nsID::GenerateUUID())`
(`toolkit/components/resistfingerprinting/nsRFPService.cpp:1361`). Именно этот
ключ солит шум, добавляемый к canvas/WebGL. Чтобы получить идентичный результат
на разных машинах, ключ надо заменить с `GenerateUUID()` на
**детерминированный seed, вычисленный из Vento-фингерпринт-профиля**
(например `HMAC(profileSeed, origin)`). Это правка точечная и локализованная.

### Предлагаемая архитектура (сквозная для всех пунктов ниже)

1. **Vento Fingerprint Profile** — структура настроек (UA, платформа, экран,
   ядра CPU, GPU vendor/renderer, шрифты, часовой пояс, локаль, audio-seed,
   canvas-seed …). Хранится/синхронизируется с backend, редактируется в
   Vento-панели. По сути расширение существующего механизма
   `privacy.fingerprintingProtection.granularOverrides` (JSON per-target
   overrides уже поддерживается — `modules/libpref/init/all.js:819`).
2. **Единый seed** профиля → из него детерминированно выводятся ВСЕ случайные
   величины (canvas/webgl/audio-шум, порядок enumeration и т.п.). Один seed на
   всех пользователей с одинаковым профилем ⇒ идентичный результат.
3. **Применение**: переиспользуем существующие точки перехвата RFP
   (`nsRFPService::GetSpoofed*`, canvas-хук, WebGL-санитайзер), заменяя
   «константа/рандом» на «значение из профиля / seed из профиля».
4. **Гарантия 100%**: любое поле, которое не покрыто профилем, должно быть
   либо приведено к значению из профиля, либо заблокировано. Нужен «deny by
   default» список поверхностей (см. `RFPTargets.inc` как готовый чек-лист из
   81 пункта).

Сложность оценивается по шкале: **Низкая / Средняя / Высокая / Очень высокая**.
Тестируемость: **Высокая** (детерминированный юнит/xpcshell), **Средняя**
(нужен реальный рендер/GPU, mochitest/marionette), **Низкая** (зависит от
железа/ОС, флейки, нужен E2E-стенд с разными машинами).

## 3. Canvas / WebGL / WebGPU / WebCodecs (графика — самый «жирный» энтропийный канал)

| Поверхность | Что собирается | Где менять | Сложность | Тестируемость |
|---|---|---|---|---|
| Canvas 2D readback | пиксельный хэш `toDataURL/getImageData` — зависит от GPU/драйвера/сглаживания шрифтов | **Ключевая правка**: детерминированный шум. Заменить `GetBrowsingSessionKey`/UUID на seed из профиля (`nsRFPService.cpp`, canvas-хук). Таргеты `CanvasRandomization`(9), `EfficientCanvasRandomization`(76). | Высокая | Средняя |
| WebGL параметры | `getParameter`, расширения, precision, VENDOR/RENDERER (`UNMASKED_*`) | Таргеты `WebGLRenderInfo`(60), `WebGLRenderCapability`(59), `WebGLVendor*`(77-79), `WebGLRenderer*`(80). Прибить vendor/renderer + все лимиты к профилю. `dom/canvas/WebGL*`. | Высокая | Средняя |
| WebGL pixel readback | хэш отрендеренной сцены (`readPixels`) | `WebGLRandomization`(75) — детерминированный шум из seed профиля. | Очень высокая | Низкая |
| WebGPU | лимиты, `isFallbackAdapter`, subgroup sizes | Таргеты 64-66. Прибить к профилю. `dom/webgpu`. | Высокая | Средняя |
| WebCodecs | поддерживаемые кодеки/конфигурации | `WebCodecs`(71). Привести список к профилю. | Средняя | Средняя |

Комментарий: это самая трудная и самая важная часть. Проблема в том, что при
реальном рендере результат зависит от GPU/драйвера/ОС. Есть два пути:
(а) **шумовая маскировка** поверх реального рендера, детерминированная из seed
(риск: базовый рендер всё равно разный → шум должен быть достаточным, чтобы
полностью перекрыть аппаратную разницу — трудно гарантировать 100%);
(б) **программный/унифицированный рендер** (SwiftShader/llvmpipe для WebGL,
software-путь для canvas-текста) — даёт байт-в-байт идентичность на всех
машинах, но бьёт по производительности и совместимости. Для гарантии «100%»
надёжнее (б) хотя бы для отпечатко-снимающих операций (readback), оставляя
аппаратный рендер для обычной отрисовки. Требует отдельного PoC.

## 9. Сетевые/протокольные отпечатки (вне JS — важно не забыть!)

Эти каналы **не покрываются** RFP и на 100% идентичности могут всё сломать:

| Поверхность | Что собирается | Где менять | Сложность | Тестируемость |
|---|---|---|---|---|
| TLS ClientHello (JA3/JA4) | набор/порядок cipher suites, расширений, GREASE | NSS/`security/nss` + `netwerk`. Нужно унифицировать ClientHello. Уже частично фиксирован сборкой, но версии ОС/NSS влияют. | Очень высокая | Низкая |
| HTTP/2, HTTP/3 fingerprint | порядок SETTINGS, приоритеты, Akamai h2 fingerprint | `netwerk/protocol/http`. Унифицировать параметры. | Очень высокая | Низкая |
| Порядок HTTP-заголовков | последовательность заголовков запроса | `nsHttpHandler`/`nsHttpChannel`. Зафиксировать порядок. | Средняя | Средняя |
| IP / геолокация по IP | адрес, ASN, страна | Решается через **Vento proxy** (уже есть `vento_proxy`). TZ/локаль профиля должны совпадать с гео прокси, иначе противоречие. | — (уже есть) | Средняя |
| DNS / QUIC особенности | — | Через прокси. | Средняя | Низкая |

Комментарий: **важный вывод** — идеальный JS-фингерпринт бессмысленен, если
TLS/HTTP2-отпечаток и IP выдают разные машины. Для «100%» этот блок обязателен и
он самый трудный (зависит от системного NSS и стека ОС). Реалистично: собрать
ClientHello/h2-параметры в единый профиль на уровне NSS-сборки Vento. Часть уже
нивелируется тем, что все пользователи Vento идут через один и тот же билд +
прокси. Требует отдельного глубокого PoC и, вероятно, патча NSS.

**Глубокий PoC по §9 выполнен** (этап 2), см.
`fingerprint/network/NETWORK_FINGERPRINT_POC.md` + модуль
`fingerprint/network/VentoNetworkFingerprint.sys.mjs`. Разбор реального кода
дерева показал: внутри одного билда Vento порядок расширений/cipher TLS (NSS **не**
перемешивает, в отличие от Chrome), supported_groups/key_share, кадр HTTP/2
SETTINGS и его порядок, порядок псевдо- и обычных заголовков — уже **константы
билда**, идентичные между машинами. Различаются лишь: per-connection рандом
(GREASE, presence ECH-grease), per-host кэш TLS-intolerance и изменённые prefs —
всё это, кроме случайных байтов GREASE и TCP/IP-стека, закрывается **только
префами** (`deterministicPrefs()`). Итог PoC: «билд + прокси» дают почти всё;
нативного патча требует ровно один пункт — детерминированный GREASE в
`tls13_ClientSetupGrease` (и то лишь для побайтового raw-JA3; JA4 GREASE
игнорирует), а IP/TCP-стек нормализует `vento_proxy`.

## 10. Действия пользователя (поведенческий/биометрический фингерпринт)

Вопрос из задачи: можно ли выровнять движения мыши, тайминги клавиатуры и т.п.?

**Что собирают сайты:**
- Динамика мыши: траектории, скорость, ускорение, кривизна, паузы.
- Клавиатурная динамика (keystroke dynamics): интервалы dwell/flight между
  нажатиями — устойчивая биометрия, различает людей.
- Тайминги скролла, паттерны тача, давление стилуса.
- Ошибки/исправления, ритм ввода, «человечность» (bot-detection наоборот).

**Что можно сделать технически:**
| Подход | Суть | Сложность | Тестируемость |
|---|---|---|---|
| Квантование таймстампов событий | `event.timeStamp` уже режется `ReduceTimerPrecision`(35)/`WidgetEvents`(36). Убирает микротайминги клавиатуры/мыши. | Средняя | Средняя |
| Скрытие координатных дельт | `MouseEventScreenPoint`(42), `MouseEvent.screenX/Y` — RFP уже приводит к клиентским. | Низкая | Высокая |
| Нормализация/переписывание траекторий | Перехватывать `mousemove` в родительском процессе и заменять реальную траекторию на **сгенерированную детерминированно из seed** синтетическую (сплайны). `widget`/`dom/events`. | Очень высокая | Низкая |
| Ресэмплинг клавиатурных интервалов | Задерживать/выравнивать доставку keydown/keyup в фиксированную сетку. | Очень высокая | Низкая |

**Теоретический вывод (для ответа на прямой вопрос задачи):**
Да, поведенческий фингерпринт теоретически выравниваем, и первый уровень
(**убрать высокоточные тайминги** через уже существующий `ReduceTimerPrecision`)
даёт большой эффект малой ценой — это надо включить и сделать джиттер
детерминированным. Но **полное** выравнивание (чтобы траектории мыши и ритм
клавиатуры двух разных живых людей стали неотличимы) на практике недостижимо
на 100% без разрушения UX: если переписывать движения на синтетические, то
(а) страдает отзывчивость и точность ввода, (б) сама «слишком идеальная»
синтетика становится отпечатком (детектор ботов). Реалистичная цель —
**понизить разрешающую способность** канала (квантование таймингов + огрубление
дельт), а не достичь побайтовой идентичности. Это следует зафиксировать как
ограничение: по поведенческому каналу гарантируем «сильно затруднить», а не
«100% идентично», в отличие от статических полей (пп.1-8), где 100% достижимо.

**Реализация (этап 2, уровень 1):** движко-независимое детерминированное ядро
`browser/components/vento/fingerprint/VentoBehavioralQuantizer.sys.mjs` —
квантование таймстампов событий (сетка + фазовый сдвиг из seed, аналог
`ReduceTimerPrecision`(35)/`WidgetEvents`(36), но джиттер детерминированный) и
огрубление координат указателя (`MouseEventScreenPoint`(42)). Точки врезки в
ядро задокументированы в `fingerprint/README.md`; детерминизм и разрушение
субгридового микротайминга покрыты `test_vento_fingerprint_behavioral.js`.
Уровень 2 (синтетические траектории/ресэмплинг) сознательно не реализуется —
по выводу выше он недостижим без разрушения UX и сам становится отпечатком.

## 11. Сводка по сложности и приоритетам реализации

**Достижимо на 100% идентичности, низкая сложность (делать первым):**
пп.1, 2, 4(список шрифтов), 6, 7(TZ/locale/Math), 8 — это всё «прибить значение
из профиля» поверх готовых RFP-таргетов. Тестируемость высокая (xpcshell/
mochitest, детерминированно).

**Достижимо, но сложно (нужен PoC, риск для 100%):**
п.3 (canvas/WebGL/WebGPU readback), п.5 (audio) — либо детерминированный шум из
seed, либо софт-рендер. Главный технический вызов проекта.

**Обязательно, но очень сложно и слабо тестируемо:**
п.9 (TLS/HTTP2/IP) — без него «100% на разных машинах» недостижимо; сильно
завязано на NSS и системный стек; частично закрывается единым билдом + прокси.

**Принципиально ограничено:**
п.10 (поведение) — реалистично «затруднить», а не «уравнять на 100%».

### Первоочередные шаги (предложение на этап 2)
1. Спроектировать структуру **Vento Fingerprint Profile** + единый `seed`,
   расширив `privacy.fingerprintingProtection.granularOverrides` и добавив
   выдачу профиля с backend + редактор в Vento-панели.
2. Заменить `nsRFPService::GetBrowsingSessionKey` (случайный UUID) на
   детерминированный seed из профиля — самая точечная и важная правка.
3. Прибить все «низкосложные» таргеты (пп.1,2,4,6,7,8) к значениям профиля,
   покрыть xpcshell-тестами (сравнение выдачи двух «машин» с одним профилем).
4. Отдельный PoC по canvas/WebGL детерминизму (шум vs софт-рендер) — принять
   решение по стратегии для «100%».
5. Отдельное исследование TLS/HTTP2-унификации (патч NSS/netwerk) — оценить,
   что даёт единый билд + прокси, что нужно дорабатывать.

### Заметки по тестированию (как проверять «идентичность»)
- Юнит/xpcshell: два `OriginAttributes`/два «профиля-инстанса» с одинаковым
  seed ⇒ побайтово равные `GetSpoofed*`/canvas-хэши. Детерминированно, в CI.
- E2E: два физически разных стенда (разные GPU/ОС) + автосбор фингерпринта
  (свой скрипт по образцу CreepJS/fingerprint.js) ⇒ сравнение JSON-снимков.
  Это единственный способ поймать аппаратно-зависимые утечки (canvas/WebGL/
  audio/TLS). Нужен отдельный стенд (расширить `vento-test-env`).
